Case study · SCORVYN.™ · Next.js

Selling sixty
of something

A limited drop is a promise with a number in it. Sixty pieces exist, one per person, and no restock — which means the interesting problem isn't the storefront, it's making sure the sixty-first sale can't happen. Not "shouldn't". Can't.

Role
Sole developer
Stack
Next.js, TypeScript, Stripe, Resend
Persistence
None — Stripe is the source of truth
Live
scorvyn.shop

1 · The database that isn't there

There is no database in this project. The count of what's sold is derived from Stripe on every check, rather than kept in a table or a Redis counter.

That started as a constraint and turned into the right answer. Stripe is the only system that knows what was actually paid, and the only one that survives a cold start, a second serverless instance, or a redeploy in the middle of a drop. Any counter I kept alongside it would be a second, weaker opinion about the same fact — and the two would disagree exactly when it mattered most.

2 · A checkout session is a hold

If only paid orders counted, two people could both be told "one left", both pay, and one would get a refund and a bad story. So a Checkout Session that has been created but not yet paid still holds its piece.

The hold needs no cleanup job, because it is the session's own lifetime: every session is created with a 30-minute expiry, and an expired session simply stops counting. Thirty minutes is Stripe's floor for expires_at, and comfortably longer than typing in a card.

3 · One per person, for several definitions of person

"One per customer" is easy to say and easy to dodge. Identity here is email, phone, and delivery address — each normalised, each hashed, and each independently sufficient to block a second order. A fresh Gmail address doesn't get you a second piece if the parcel is going to the same door.

Both rules live server-side, in the one place that can actually create a charge. Everything the storefront does — greying a button, printing "SOLD OUT" — is decoration on top. A caller who skips the UI and POSTs straight at the API hits precisely the same wall.

4 · Which way to fail

The storefront asks a status endpoint whether the drop is open. That endpoint and the checkout endpoint read the same underlying fact, and fail in deliberately opposite directions.

Behaviour when Stripe can't be reached
Checkout Fails closed — it does its own read at the moment of charging, and refuses if it can't confirm.
Drop status Fails open — answers "unknown" rather than "sold out".

The asymmetry is the whole point. A blip in a read-only display must never hang a closed sign on a shop that still has stock; a blip at the till must never sell something that isn't there. The status endpoint can be wrong for fifteen seconds and the worst case is a slightly stale page. It cannot sell a sixty-first piece, because it is never consulted before a sale.

5 · The number nobody gets to see

The status response says open or closed. It does not say how many are left, and that omission is deliberate: the response is public, anyone can read it in devtools, and a live count is the one thing that turns a scarce object into a countdown. The server knows the number. The customer knows whether they can buy.

6 · Numbering by counting, not incrementing

Pieces are printed in purchase order, so each order needs its position. That number is derived by counting paid sessions in Stripe rather than bumping a counter — because the webhook's de-duplication set lives in process memory and won't survive a cold start, and a redelivered webhook would eventually hand one order two different numbers. Counting can't do that: the same session always lands in the same place, and the count is correct from the very first run with no backfill.

The cost, stated plainly in the code: a session that pays late slots in ahead of newer orders and shifts their numbers. The shop is card-only, so sessions settle synchronously and this is close to theoretical — but it's a real trade, and it goes away the day orders get persisted properly.

7 · The unglamorous parts

Checkout and the contact form are unauthenticated by design, so both sit behind a per-IP budget and a much looser global one. The client IP comes from X-Forwarded-For, which a direct caller can forge — which is exactly why the global ceiling exists as a backstop. Counters live in Redis when credentials are present so the budget is shared across serverless instances, and fall back to process memory when they aren't, logging once per cold start rather than silently disappearing.

The order-limit, sequence, origin-check and alert-email modules carry 60 tests between them. They're the parts where being wrong costs money or trust, which is a reasonable rule for where to spend testing effort on a project this size.

What I'd change

Deriving everything from Stripe is elegant until the shop outgrows one drop. Every check is an API call, cached for only fifteen seconds, and the sequence code already has to page through results — thirty pages of a hundred before it gives up. Persisting orders properly would remove the paging, the late-payment reordering caveat, and the cache window all at once. The current design is right for sixty pieces and would be wrong for six thousand.
